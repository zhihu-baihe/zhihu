## 2. 四个问题的根因诊断

### 2.1 地面：密、重复、反光过强

**证据一（贴图内容）**：`PavingStones151_1K-JPG_Color.jpg` 是**扇形/扇形弧排列的小方砖**，
1K 贴图里约 20×20 块。按 `world_scale = 0.28`（= 每 3.57 m 一个贴图周期）换算：

```
单块砖边长 = 3.57 m ÷ 20 ≈ 0.18 m
```

正常石板路 0.4—0.6 m。**当前砖块尺寸只有正常值的 1/3**，这正是「过密」的量化解释。
而且扇形图案本身有强方向性，周期重复时会出现明显的「贝壳纹」重复感 —— 这就是「重复明显」。

**证据二（反光）**：

| 参数 | 当前 | 问题 |
|---|---|---|
| 街面 `roughness` | 0.42 | 石板不该这么光 |
| SSR `fade_in` | 0.2 m | 从相机脚下 0.2 m 就开始反射 → 整条街都是镜面 |
| SSR `max_steps` | 48 | 反射过完整，远处也清晰 |
| SSR `depth_tolerance` | 0.2 | 过于严格，反射出现「切片」但范围大 |

**修正方案（分两半）**
- **零素材**：`roughness 0.42 → 0.66`；SSR `fade_in 0.2→1.2`、`max_steps 48→24`、`depth_tolerance 0.2→0.42`、`fade_out 12→8`。目标：**只有水面与近处湿地有反射**。
- **需换素材**：街道主铺装换成「方形石板 / 条石」贴图。

**候选素材（ambientCG，CC0，已查询确认存在）**

| assetId | 说明 |
|---|---|
| `PavingStones150` | 常与 151 同系列，需实测砖块尺寸后决定 |
| `PavingStones138` / `128` / `142` / `146` / `147` | 方形铺装候选 |
| `PavingStones070` | 常见于「大块方石板」 |
| `PavingStones047` | cobblestone（鹅卵石，可做河埠次铺装） |

> 筛选方法：下载后先量「单块砖在贴图里占多少像素」→ 反推 `world_scale` 使单砖落在 **0.45—0.55 m**。
> 这一步我会写成脚本一次算好，不用肉眼试。

### 2.2 屋顶过黑、墙面空白

**屋顶（三重压暗，已确认为硬缺陷）**

```
贴图 RoofingTiles013A 实测平均亮度 0.193 (sRGB) → 线性 ≈ 0.031
tint  #46525e = (0.27,0.32,0.37) sRGB          → 线性 ≈ 0.08
albedo = 0.031 × 0.08 ≈ 0.0025（线性）≈ 反射率 0.25%
现实青瓦反射率 ≈ 0.10—0.15 → 相差约 50 倍
```

再叠加「环境光来源 = SKY，而 `sky_top = #0d1730` 极暗」→ 朝上的屋面几乎拿不到任何光。
**结论：RoofingTiles013A 不适合做夜景青瓦**（它本身是暗色石板状纹理，且形态不是中式筒瓦/板瓦）。

**墙面（亮度正常，缺构造）**

```
贴图 Plaster001 实测 0.831 (sRGB) → 线性 0.66
tint  #bdb1a0 → 线性 ≈ (0.51,0.44,0.36)
albedo ≈ 0.30 线性 → sRGB ≈ 0.58（浅灰白，正常）
```
所以「空白」不是亮度问题，而是**立面缺少构造层次**。当前中式建筑只有
格子窗 + 檐柱 + 额枋 + 门洞 + 台基，**没有勒脚、腰线、窗套、墙头压顶**。

**修正方案**
- 屋顶：`roof/roof_dark` 的 tint 提亮到接近白（`#c8d2dc` 系），**并换瓦贴图**（这是硬性的）。
  候选：`RoofingTiles012A/B/C`、`RoofingTiles011A`、`RoofingTiles014B`、`RoofingTiles015A`。
  挑选标准：**平均亮度 0.35—0.55、筒瓦/板瓦形态、冷灰调**。
- 墙面：加**勒脚**（石砌墙脚，高 0.5 m，一个盒体）与**墙头压顶线**——这两个是真实构件、不是装饰堆砌，
  且各只需 1 个盒体，不违反「不要用几何体假装细节」。
  > **执行修正（2026-10-15，B4）**：勒脚做了，高 0.36 m（不是 0.5 —— `0.28 + 0.50 = 0.78` 会把檐柱柱础整个吞进石活里）。
  > **「墙头压顶」对民居不成立**：`eave_h = h − 0.12` 且屋面比墙外皮多出 0.9 m，
  > 墙外皮那一竖线上的屋面高度已是 `h + 0.02` → 墙顶永远在屋面之下，做出来没人看得见。
  > 改成把它放在真正需要压顶的地方：**勒脚顶上的压顶石**（`PlinthCap`，0.64→0.76，再出挑 0.07）。
  > 同一步里还顺手修了一个老缺陷：**三级踏跺从建成起就全部埋在台明板里**（`dist` 是相对建筑中心量的），
  > 详见开发日志「第十次追加」。
- tint 口径修正：把 tint 从「中间亮度颜色」改为「接近白的色调」，
  统一改一遍 `palette`（影响屋顶/木板/街面三处）。

**候选素材**

| 类别 | 候选 |
|---|---|
| 屋面瓦 | `RoofingTiles012A/B/C`、`011A`、`014B`、`015A` |
| 墙面 | `PaintedPlaster017`（带涂装质感，比 Plaster001 更有信息量）、`Plaster007/002/003/004` |
| 墙基 | 已有 `Bricks075A`（夯土砖，亮度 0.517，**已下载但未接入**） |

### 2.3 灯笼：过亮、光斑强、排列机械

**过亮 / 光斑**
```
灯笼自发光 1.7 + glow 0.45 / bloom 0.20 → 灯体过曝成白球
动态光 1.9 × LIGHT_ENERGY_SCALE 0.75 = 1.425，range 8.5，omni_attenuation 默认 1.0
shadow_enabled = false（保持，性能考虑）
```
**修正**：自发光 `1.7 → 1.25`；动态光 `1.9 → 1.55`；range `8.5 → 6.5`；
`omni_attenuation 1.0 → 1.6`（衰减更柔，消除硬边光斑）。

**排列机械（四条周期性的叠加）**

| 项 | 现状 | 修正 |
|---|---|---|
| 间距 | 每行等距 | 位置抖动 ±0.30 m |
| 高度 | 每行等高 | 高度抖动 ±0.35 m |
| 形状 | `i % 2` 严格交替 | 按权重随机（球 60% / 柱 25% / 方 15%） |
| 尺寸 | 固定 | 随机 0.85—1.16 |
| 亮度 | 固定 | 随机 ±12% + 极轻微呼吸（±3%，周期 3—6 s 各不同） |
| 排列 | 直线插值 | 保持直线（街道本来就是直的），但**每行加一个固定相位偏移**避免两行镜像对称 |

**动态光预算**：现在是 29/30。抖动后不会增加数量，但我会改成**按灯具重要性分配**
（近处/桥头/城门给动态光，远处只保留自发光）→ 预计可降到 24—26 盏，留出余量。

### 2.4 街道空旷、道具不足、远景缺焦点

**主因：建筑没排满（这是布局问题，不是装饰问题）**

```
主街 z = 40 → −20（长 60 m）
西侧建筑（yaw 90，正面朝街）：z = 24 / 14 / 4，进深 10 m
  → 覆盖 z ≈ 29 → −1，即 30 m
  → 空缺：z = 40~29（11 m）与 z = −1~−20（19 m），合计 30 m
东侧建筑（yaw 270）：z = 24 / −9 / −19
  → 覆盖 19~29、−14~−4、−22.5~−15.5
  → 空缺：z = −4~19，即 23 m
```

**走在主街上，两侧近一半是空白地** —— 这才是「空旷」的真正原因。
补建筑是**数据层改动**（`map_moyi.json` 的 `buildings` 数组加几条），复用现有生成器，**零新增素材**。

**次因：可交互/可看的物件密度低**
1058 m² 铺装上只有 25 个道具 + 7 个摊位，且集中在夜市与河埠。

**远景焦点**
玩家出生在 `[0, 0.2, 34]`，朝北（−Z）。北侧远景依次是：河（−22~−31）→ 桥（−20~−40）→
对岸塔（−74）→ 7 座山。雾在 60 m 处透过率 52%，所以**桥与塔被雾压得偏淡**。
修正：给对岸塔与城门加**轮廓灯**（暖色点光 + 自发光窗），让它成为「远处有一个你想走过去的地方」。

## 4. 人物模型替换方案

### 4.1 现状评估：**结构已就绪，替换成本很低**

实测确认（见 §1.3）：

- ✅ `Model` 是**独立空容器**，玩家与 NPC 都有。
- ✅ 移动（`CharacterBody3D` + `_physics_process`）、碰撞（`Collision/CollisionShape3D`）、
  相机（`CameraYaw/SpringArm3D/Camera3D`）、交互（`Interactor` / `Interactable`）、任务、存档
  **全部不依赖模型**。
- ✅ 朝向由 `model.rotation.y` 控制（操作的是 `Model` 节点，不是 rig）。
- ✅ 体型由 `model.scale` 控制（NPC 的 `scale` 参数）。
- ⚠️ **唯一耦合**：`player_controller.gd:28` 与 `npc_actor.gd:13` 声明了 `var rig: HumanoidRig`
  （强类型），并在两处调用 `rig.set_locomotion(speed)`。

### 4.2 最小修改方案（4 处改动）

**思路**：把「视觉表现」抽象成一个只要求 `set_locomotion(speed)` 的接口，
程序化人形与 GLB 适配器都实现它。控制器只认接口，不认具体类型。

```gdscript
# player_controller.gd / npc_actor.gd —— 只改这两行
-  var rig: HumanoidRig = null
+  var visual: Node3D = null        # 任何实现了 set_locomotion() 的节点

   # 调用处加一层保护（本来就有 null 判断）
-  if rig: rig.set_locomotion(hspeed)
+  if visual and visual.has_method("set_locomotion"):
+      visual.set_locomotion(hspeed)
```

**新增一个适配器**（不改任何现有脚本逻辑）：

```gdscript
# scripts/actors/character_visual_glb.gd（新增）
class_name CharacterVisualGLB
extends Node3D
## 把外部 GLB 人物模型适配成本项目要求的视觉接口。
## 职责：缩放校正 / 朝向校正 / 落地校正 / 动画驱动。
@export var model_path: String = ""
@export var target_height: float = 1.72
@export var face_negative_z: bool = true   # glTF 默认 +Z 朝前，本项目需要 −Z

var _anim: AnimationPlayer
var _skeleton: Skeleton3D
var _speed := 0.0
func set_locomotion(speed: float) -> void: ...
```

`humanoid_builder.gd` 增加一个分支：`cfg` 里有 `glb_path` 时走 GLB，否则走现有程序化人形。
**玩家与 NPC 的生成入口不变**，只是换了个实现。

### 4.3 接入 GLB 时必须逐项检查（含一个必踩的坑）

| # | 检查项 | 方法 | 本项目的期望值 |
|---|---|---|---|
| 1 | **朝向** | **⚠️ 关键坑**：Blender 的「前」是 −Y，导出 glTF 后变成 **+Z**；而本项目要求模型正面朝 **−Z** | 加载后**必须实测截图确认**，若相反则 `rotation.y = PI`。**不要假定** |
| 2 | 缩放 | `MeshInstance3D.get_aabb().size.y` | 应为 **1.72 m**；若是 1.8 或 0.0172（厘米单位）→ `scale = 1.72 / 实测高` |
| 3 | 落地 | 遍历子网格取 AABB 的 `min.y` | 应 ≈ **0**（脚底贴地）。若不是 → `position.y -= min_y` |
| 4 | 材质 | 直接看渲染 | GLB 自带材质可能过饱和/过亮，与本场景蓝调冲突 → 需要 `material_override` 或降饱和 |
| 5 | 动画节点 | 打印 `find_children("*", "AnimationPlayer")` / `"Skeleton3D"` | 有则接 `AnimationTree`；无则退回程序化摆动（若模型无骨骼，无法程序化驱动） |
| 6 | 骨骼兼容 | 对比新模型的骨骼命名与现有动画 | **本项目目前没有骨骼动画文件**（动画全是程序化计算），所以新旧骨骼不兼容问题**不存在**——这是当前架构的一个意外优势 |
| 7 | 碰撞 | 对比 AABB 与 `CapsuleShape3D(r=0.34, h=1.7)` | 模型比碰撞体宽很多时需要调碰撞体；否则会「看起来穿墙」 |
| 8 | 相机 | 跑一遍 | 确保 SpringArm 仍能避障，且模型没有挡住镜头 |
| 9 | 名字标签 | NPC 的 `NameLabel` 在 y=2.16 | 若新模型更高，标签要同步上移 |

### 4.4 如果新模型带 Skeleton3D 与动画

- **有动画**：适配器用 `AnimationTree` 做 walk/idle 混合，`set_locomotion(speed)` 映射为
  `blend_position` 或播放速率。**不需要改控制器**。
- **有骨骼但无动画**：可以写程序化骨骼驱动（复用现有 `HumanoidRig` 的相位算法，
  改写成旋转 `Skeleton3D` 的骨骼），但需要先确认骨骼命名与朝向轴向 —— 这一步无法凭空完成，
  需要拿到实际模型后才能判断。
- **无骨骼无动画**：只能整体位移/轻微摇摆，效果差于当前程序化人形。**不建议**。

### 4.5 现在就能做的准备（等你给模型再做）

1. 把 `rig` 改成接口（4 行改动）—— 这一步**不影响当前任何表现**，是纯粹的架构准备。
2. 加 `CharacterVisualGLB` 适配器骨架（含缩放/朝向/落地自动校正逻辑）。
3. 在 `assets/` 下建 `characters/` 目录约定：`assets/processed/characters/<id>/<id>.glb` + 同名贴图。
4. 给自检加一条：加载指定 GLB 后校验 高度≈1.72 / min_y≈0 / 正面朝 −Z。
